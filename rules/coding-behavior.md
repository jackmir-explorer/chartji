# rules/coding-behavior.md — 코딩 행동 가이드라인

LLM 코딩에서 반복되는 네 가지 실수를 막기 위한 기본 원칙.
chartji는 의료 도구 — 잘못된 가정은 환자 안전 리스크로 직결된다.

원전: Andrej Karpathy 관찰 기반 4원칙 (forrestchang/andrej-karpathy-skills).

---

## 1. Think Before Coding — 가정 드러내기

- 가정은 명시한다. 불확실하면 미르에게 질문한다.
- 해석이 여럿이면 나열한다. 임의로 고르지 않는다.
- 더 단순한 방법이 있으면 말한다. 필요하면 되묻는다.
- 불분명한 지점은 멈춘다. 무엇이 혼란스러운지 이름 붙이고 묻는다.

## 2. Simplicity First — 요청한 만큼만

- 요청되지 않은 기능 금지
- 단일 사용처에 추상화 금지
- 요청되지 않은 "유연성·설정 가능성" 금지
- 일어나지 않는 상황에 대한 에러 처리 금지
- 200줄이 50줄로 가능하면 다시 쓴다

판정 질문: "시니어 엔지니어가 보면 과복잡하다고 할까?" → 그렇다면 단순화.

## 3. Surgical Changes — 필요한 것만

- 요청하지 않은 인접 코드·주석·포매팅 변경 금지
- 깨지지 않은 것 리팩터 금지
- 기존 스타일 매치 (내 취향과 달라도)
- 관련 없는 죽은 코드는 언급만 — 삭제 금지
- 변경된 모든 줄이 요청에 직접 추적되어야 한다
- `src/*.js` (컴포넌트·app·prompts 등) 수정 시 **`src/index.html`의 `?v=...` 쿼리스트링 동시 bump** — 브라우저 캐시 우회 (2026-04-24 Wave 2 QA 사례: `?v=L3-smoke` 미변경으로 신규 panels.js 미적용)

## 4. Goal-Driven Execution — 검증 가능한 목표

작업을 검증 가능한 형태로 변환:
- "검증 추가" → "잘못된 입력 테스트 작성 → 통과시키기"
- "버그 수정" → "버그 재현 테스트 작성 → 통과시키기"
- "X 리팩터" → "전후 테스트 모두 통과 확인"

다단계 작업은 단계별 검증 체크를 포함한 짧은 계획을 먼저 제시.

---

## 역할별 중점 매핑

| 역할 | 중점 원칙 |
|---|---|
| Boss | Think Before + Goal-Driven (전략 가정·성공 기준) |
| Designer | Think Before + Goal-Driven (범위·검증 기준 정의) |
| Builder | Simplicity + Surgical (명세 외 금지) |
| Reviewer | Surgical 검증 (모든 라인이 설계서에 추적되는가) |
| QA | Goal-Driven 검증 (성공 기준 달성 여부) |

---

## 작동 징후

이 가이드라인이 작동하고 있다면:
- diff에서 불필요한 변경이 줄어든다
- 과복잡화로 인한 재작업이 줄어든다
- 구현 후가 아니라 **구현 전에** 질문이 나온다
