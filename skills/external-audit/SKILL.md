# skills/external-audit/SKILL.md — External Audit (외부 감사)

## 목적
**기존 시스템·구조·자산이 장기 운용에 적합한지를 외부자(=과거 결정의 맥락에 매이지 않은 시각)로 진단**한다.

Boss/Architect/Designer가 **제안된 변경**을 검토하는 것과 다르다. External Audit은 **현재 정착된 구조 자체**를 감사 대상으로 삼는다.

호출 전형:
- "이 스키마/패널/지식체계를 외부감사 관점으로 봐줘"
- Boss가 "10년 운용 적합성 진단" 필요 시 본 skill 선행 호출 → 결과를 CMO·CLO·CFO·CVO 4관점 판정의 입력으로 사용

---

## 입력
- **감사 대상**: 파일·폴더·구조·계약 (예: `knowledge/` 전체 / 패널 contract / 진료 5단계 커버리지)
- **감사 기준 시간 지평**: 명시적 — "10년", "Phase N 완료 시점", "엔트리 N개 시점" 등
- **감사 렌즈**(선택): 운용성·확장성·임상 안전·법적 리스크 중 강조 축

> 시간 지평이 명시되지 않으면 감사 시작 전 미르에게 질문. **추정 금지**.

---

## 호출 금지 케이스
- **이미 제안된 변경**의 검토 → Boss / Architect / Designer 경로
- **단일 함수·코드 블록**의 결함 → Reviewer
- **명세 문서 표준 준수 여부** → Auditor (`agents/auditor.md`)
- **감사 결과 그 자체의 구현** → 별도 Wave (Designer → Builder)

External Audit은 **진단만 한다**. 권고가 채택되어도 구현은 정규 워크플로우(Architect → Designer → Builder)로 이관된다.

---

## 절차 (10단계)

### 1. 감사 범위 정확히 한정
- 대상 파일·폴더 목록을 **명시적으로 열거** (산문 대신 경로 리스트)
- 감사 기준 시간 지평 1줄 선언
- 감사 렌즈 1~3개 선언

### 2. 사전 정찰 (Recon)
- 대상의 실제 콘텐츠 5~10개 sample 읽기 (전수 아님)
- 관련 rule 문서·설계 세션·skill 정의 읽기
- 현재 운영 중인 파이프라인·계약 확인
- **감사인은 미르의 과거 결정 맥락을 먼저 파악**한 뒤에 비판한다

### 3. 강점 인식 (보존할 것)
- 잘 설계된 구성 요소 3~5개 식별
- 각각에 대해 "왜 이게 드문 자산인가" 1줄
- **이 단계 생략 금지** — 강점 인식 없는 감사는 파괴적이며 신뢰를 잃는다

### 4. 약점 진단 (시간 지평 렌즈 적용)
약점을 3 카테고리로 분류:

| 카테고리 | 정의 | 처리 |
|---|---|---|
| **A. 지금 안 심으면 영원히 못 심는 것** | 메타필드·관계 구조·신선도 추적 등 | **즉시 채택 권고** |
| **B. 중요하지만 데이터 축적 후 가능** | 의미론 검색·외부 공유 포맷 등 | **유보 권고 (1년 후)** |
| **C. 운영 개선** | UI 개선·검색·자동화 | **Wave 분리 권고** |

각 약점에 대해:
- 현재 비용(숨은 cost) 1줄
- 미래 비용(증폭 시점·배수) 1줄
- 재설계 난이도 1줄

### 5. 의도 vs 누락 판정
공백·회피로 보이는 항목은 반드시 다음을 묻는다:
- **의도된 설계인가?** (과거 결정 기록 추적)
- **당시 전제가 현재도 유효한가?** (knowledge 성숙도·scope 변경 등)
- **봉인된 코드/데이터 잔존하는가?** (재활성화 가능 여부)

→ "의도된 회피"·"미결 봉인"·"단순 누락" 셋을 명확히 구분.

### 6. 옵션 비교 (해당 시)
변경이 다층 옵션을 가진 경우:
- 소극적 / 중간 / 적극적 3안 비교 표
- 각 안의 위험·이익·권고 1줄
- 외부 감사 권고는 **하나만** 선정 (양다리 금지)

### 7. 구체적 권고 (스키마·코드 레벨)
권고는 추상이 아니라 **구체 형태**로:
- 스키마: JSONC/YAML 예시
- 코드: 파일 경로 + 함수명/주석 위치
- 절차: Wave별 단계
- 마이그레이션: big-bang 금물, 점진 경로 + 자연 승격 규칙

### 8. 자기 점검 (Counterargument)
감사인 자신이 반대 의견 제시:
- "이 권고가 over-engineering 아닌가?"
- "이 권고가 다른 anchor를 만들지 않나?"
- "이 권고가 실증 없이 가설 수준 아닌가?"

각 반대 의견에 대해 감사인의 응답 1~2줄.

### 9. 결단 포인트 도출 (미르에게 위임)
감사인은 결정하지 않는다. 미르가 결정할 항목 3~5개를 명시:
- 각 항목 옵션 표기 (A/B 또는 즉시/유보 등)
- 선결 의존 관계 명시 (D2는 D1 선결 등)

### 10. 감사 종결 사인
정형 포맷:
```
판정: PASS / CONDITIONAL PASS / INCOMPLETE BY DESIGN / STOP
조건: (CONDITIONAL PASS의 경우 채택 조건)
권고 조치: (즉시 vs 유보 vs Wave 분리)
결단 주체: 미르 (+ 필요 시 Boss 경유 권장)
재감사 시점: (예: 6개월 후, Wave 1 완료 후)
```

## 주의사항

### 강점 먼저 — 절대 생략 금지
약점만 나열하는 감사는 신뢰를 잃는다. 보존할 자산을 명시하면 권고가 무엇을 부수지 않을지가 분명해진다.

### 시간 지평을 명시 — "10년"이 핵심 렌즈
시간 지평을 명시하지 않은 감사는 모든 약점을 동등하게 다룬다 → over-engineering 유도. **시간 지평이 약점의 등급을 결정**한다.

### 자기 점검 단계 생략 금지
감사인이 자신의 권고에 반대 의견을 먼저 제시하지 않으면 미르가 그 작업을 떠안는다. 감사인이 미리 부담을 진다.

### 결정하지 말고 결단 포인트만 도출
감사인은 권고할 뿐 결정하지 않는다. 미르가 결정할 항목을 명시 — 각 항목에 옵션·의존관계 표기.

### Big-bang 마이그레이션 권고 금지
모든 권고는 점진 경로를 가져야 한다. "예약석 심기"(빈 메타필드 선제 삽입), "병존 후 자연 퇴장"(parents → relations), "신규 ingest부터 적용" 패턴 활용.

### 감사 보고서 자체는 최종 결정 아님
보고서는 Boss 4관점 판정의 입력. 감사인이 즉시 채택을 권고해도 Boss CMO/CLO/CFO/CVO 검토를 통과해야 채택. 외부 감사 보고서가 단독으로 Builder 진입의 근거가 될 수 없다.

### 감사 결과는 reports/ 폴더에 저장
파일명: `reports/YYYY-MM-DD-external-audit-[대상].md`
Boss 후속 검토는 `reports/YYYY-MM-DD-boss-report-[대상].md`로 분리.

## Boss와의 연동 패턴

```
미르: "knowledge 체계를 10년 지평으로 외부감사 해줘"
  ↓
Claude (또는 Boss): External Audit skill 호출
  ↓
산출물: reports/YYYY-MM-DD-external-audit-knowledge.md
  ↓
미르 검토 → 권고 중 채택 여부 판단 필요 시
  ↓
미르: "Boss에게 검토 맡겨줘"
  ↓
Boss: 권고 항목만 추려 4관점 판정
  ↓
산출물: reports/YYYY-MM-DD-boss-report-knowledge.md
  ↓
미르 결단 → Architect → Designer → Builder
```

**중복 검토 방지 원칙**: Boss는 외부 감사의 *권고 자체*만 판정한다. 배경·옵션 비교·위험 분석은 외부 감사 단계에서 이미 수행됐으므로 Boss가 재수행하지 않는다.
